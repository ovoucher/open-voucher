# stellar.toml (SEP-1) for the voucher assets

SEP-8 wallets find a regulated asset's approval server through the issuer's `home_domain`
and the `stellar.toml` served at `https://<home_domain>/.well-known/stellar.toml`. Each
voucher asset is listed with `regulated = true`, `approval_server` and
`approval_criteria`.

The file below was generated by

```bash
cd app && node dist/src/cli.js issue --programme KE-PILOT-SIM --config ../data/seed/programme.json --offline
```

Notes on this output:

- **Placeholder keys and domain.** The issuer is the simulation-only key from
  `app/src/keys.ts`, and `voucher.example.org` is a placeholder domain. Nothing is published
  at that domain.
- **Real deployment.** With `ISSUER_SECRET` set and without `--offline`, the same command
  prints the file for the real issuer.
- **`approval_criteria`.** It is the plain-language `summary` from `rules.json` plus
  `sha256(rules.json)`. That same hash is the `MEMO_HASH` of every approved payment, so a
  wallet or auditor can match on-chain payments to the published rules.

## Before publishing

- **Anchored flag.** `is_asset_anchored = false`: a voucher is an entitlement, not a
  claim on an off-chain reserve. Par redemption for USDC is a promise the `redeem_pool`
  float backs, and its coverage is public (`coverage()`). Whether a regulator would treat a
  redeemable USD-denominated voucher as stored value is an open question (Assumption, not
  researched; see `VALIDATION.md`).
- **Status field.** `status = "test"` must stay until a pilot. Switch it to `live` only
  with a real issuer, a real domain and a funded pool.
- **`[DOCUMENTATION]`.** SEP-1 recommends an `ORG_NAME`, `ORG_URL` and support contact for
  the issuing agency. Add these when the agency is known. None is invented here.
- **CORS.** Serve the file with `Access-Control-Allow-Origin: *`, as SEP-1 requires.
